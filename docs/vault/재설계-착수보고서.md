## 0. 왜 지금 재설계하는가

두 저장소(`quant_trading_kiwoom`, `market_report`)가 파일 하나(`engine.json`)로
맞물려 돌고 있었다. 이 분리가 실제로 낳은 사고들:

| 사고 | 원인 |
|---|---|
| 수집기가 EC2에서 `ImportError` | 한쪽만 배포돼 `feeds.py`가 낡음 |
| 리포트 태그가 엔진에 도달 못 함 | 두 저장소의 어휘가 달랐다 (`NEWS`/`RANK` ↔ `EVENT`/`TREND`) |
| 토스 토큰 상호 무효화 | 같은 client_credentials를 두 저장소가 공유 |
| 배포 7커밋 뒤처짐 | 어느 쪽을 언제 올렸는지 추적 불가 |

전부 "경계가 파일이라 컴파일러도 테스트도 못 잡는다"는 한 가지 원인이다.
저장소를 합치면 이 부류가 **테스트로 잡히는 문제**가 된다.

## 2. 확정 아키텍처

> **모듈러 모놀리스** — 평면 경계는 이벤트 로그, 거래 코어는 결정론적 사이클,
> 주문은 상태 머신, 판단은 생산자 귀속, 백테스트는 밀폐된 적합도 함수.

### 2.1 4평면

평면을 **기능**이 아니라 **틀렸을 때 잃는 것**으로 나눈다.

| 평면 | 틀리면 | 허용되는 것 |
|---|---|---|
| 수집 | 데이터가 빈다 | 스크래핑, LLM, 실패, 재시도 |
| 분석 | 종목 선정이 나빠진다 | LLM, 느린 배치 작업 |
| **거래** | **돈을 잃는다** | 결정론적 코드만. 네트워크 예외는 어댑터에서 삼킨다 |
| 제어 | 다음 세션이 나빠진다 | 자동 조정, 실험, 롤백 |

### 2.2 패키지 레이아웃

최상위 `core/`·`trade/` 같은 일반명은 설치 환경의 다른 패키지와 충돌한다 —
`quant/` 네임스페이스 아래 둔다.

```
quant/
  core/      # 순수. quant 안에서 자기 자신만 안다
             #   models(Bar,Quote,Order,Fill,Position,Signal,Judgment)
             #   ports  clock  session  fx  portfolio  report_clock
  collect/   # 수집 평면 — quotes(ingest), collector, sources
  analyze/   # 분석 평면 — entities, scoring, render, watch_scorer, market_brief
  trade/     # 거래 평면 — strategy, risk, regime, oms, loop, control
  control/   # 제어 평면 — ledger, governor, selections, banker
  adapters/  # 네트워크·디스크 I/O 는 오직 여기 — brokers, notify, data, http, env
  apps/      # 진입점 — cli.py(거래), report_cli.py(수집·리포트), assembly.py
```

진입점: `python -m quant.apps.cli`, `python -m quant.apps.report_cli`.

### 2.3 무엇이 이벤트이고 무엇이 아닌가

| 구간 | 방식 | 허용 지연 |
|---|---|---|
| 뉴스 수집 → 저장소 | append-only 이벤트 로그 | 30분 |
| 저장소 → 리포트 | 로그 읽기 | 하루 |
| 리포트 → 유니버스 | 파일 | 하루 2회 |
| 시세 push → 캐시 | **진짜 이벤트**(키움 WS) | 초 |
| **캐시 → 전략 → 리스크 → 주문** | **결정론적 폴링 사이클** | `poll_seconds` |
| 원장 → 스코어보드 → 거버너 | 로그 읽기 | 주 1회 |

**시세는 이벤트로 받고, 전략은 폴링으로 읽는다.** 이미 그렇게 돼 있다 —
`_handle_real` → `_set_quote`가 캐시에 쓰고, 루프는 `quote(symbol)`로 읽는다.
이벤트가 전략 평가를 촉발하지 않는다.

거래 루프를 event-driven으로 만들면 안 되는 이유:

1. **백테스트 동일성** — `run_cycle`이 순수 함수라 백테스트와 paper가 같은 코드를
   쓴다. 핸들러가 되면 백테스트가 이벤트 버스를 흉내내야 하고, 그 흉내와 실제의
   차이가 백테스트 숫자를 못 믿게 만든다.
2. **자본 배분 경합** — 전략들이 같은 리스크 예산을 쓴다. 핸들러가 각자 반응하면
   누가 예산을 먼저 가져가는지가 메시지 도착 순서에 달린다. 재현이 안 된다.
3. **감사 가능성** — 사이클 하나 = "이 시각, 이 가격, 이 판단" 한 덩어리.

## 3. 기각한 대안: Kafka 마이크로서비스

검토했고 **기각**한다. 목표(장애 격리, 결합도 완화)는 맞지만 수단이 규모를 넘는다.

| 제안 | 기각 사유 |
|---|---|
| Kafka / RabbitMQ | EC2 **한 대**. 브로커가 죽으면 "격리됐다"던 매매 엔진이 시그널을 못 받는다. 지켜야 할 데몬만 늘어난다 |
| 뉴스 → 큐 → "매매 시그널" → 매매 엔진 | **화살표가 뒤집혀 있다.** 스크래핑한 뉴스가 주문까지 직행한다. 우리는 뉴스가 *유니버스만* 편집하고 진입은 결정론적 전략이 가격으로 판단하도록 일부러 막아뒀다 |
| Go / C# 집행 엔진 | 5·15분봉이라 레이턴시 문제가 없다. 검증된 파이썬을 버릴 이유가 없다 |
| 키움 Windows OCX | 리눅스에서 REST/WS를 쓴다. 그리고 키움으로 주문하지 않는다 (집행은 토스 단일) |
| 시차별 자원 최적화 | 한 대짜리 상시 인스턴스. 아낄 게 없다 |
| Celery / Airflow | systemd 타이머가 이미 크론 10개를 돌린다 |

Kafka가 주는 것(내구성 있는 append-only 로그, 재생 가능, 소비자 분리)은 **이미
JSONL로 하고 있다.** 다른 점은 파일이 죽지 않는다는 것뿐이다.

**단, `core.ports.EventLog`는 `read(topic, since_offset)` 형태로 둔다.** 지금
구현은 로컬 JSONL이지만, 박스가 둘 이상 되면 S3나 Redis Streams로 어댑터만
갈아끼울 수 있어야 한다. *지금 만들지 않되, 만들 수 없는 포트를 만들지 않는다.*

마이크로서비스로 갈 조건 (셋 다 현재 해당 없음):
- 초 이하 집행이 필요해짐
- 박스가 둘 이상이 됨
- 사람이 둘 이상이 됨

## 4. 저장 전략 — MySQL 경계선

### 4.1 원칙

> **아티팩트가 진실, DB는 색인.**

이미 쓰고 있는 원칙의 확장이다 (수집기에서 "JSONL이 진실, md는 뷰").
거래 엔진은 **항상** 로컬 파일에 쓴다. 적재기가 그 파일을 MySQL로 옮긴다.
MySQL이 죽어도 매매는 돈다. 분석 DB가 뒤처질 뿐이다.

### 4.2 어디에 무엇을 두나

| 데이터 | 저장소 | 이유 |
|---|---|---|
| 포트폴리오 상태, control 플래그 | **로컬 파일** | 09:15에 DB가 딸꾹질하면 매매가 멈춘다 |
| 체결 원장 (`trades.jsonl`) | **로컬 파일** → MySQL 적재 | 원본은 append-only 파일. DB는 사본 |
| OHLCV 봉 | **Parquet** | 컬럼너·압축·범위 스캔. MySQL은 시계열에서 하위 호환 |
| 뉴스 기사 | JSONL(원본) → **MySQL** | 관계 질의가 여기서 필요해진다 |
| 종목·리포트·선정·판단 | **MySQL** | 조인이 본질 |
| Obsidian 볼트 | 생성된 md | 사람과 에이전트가 읽는 뷰 |

### 4.3 MySQL이 실제로 푸는 문제

지금 "이 종목을 왜 샀지? 어떤 기사 때문에?"에 답하려면 두 저장소의 JSONL을
손으로 조인해야 한다. **그리고 그 질문이 개선 루프 전체의 핵심 질문이다.**

관계 스케치:

```
article ──< article_symbol >── symbol ──< selection ──< judgment
                                  │                        │
                                  └──< trade ──────────────┘
                                        │
                                        └── forward_return (T+1/5/20)
```

`forward_return`은 **사후에 갱신**된다 — append-only JSONL이 잘 못 하는 일이고,
Phase 7 리더보드가 반드시 필요로 하는 것이다.

### 4.4 운영 주의

- MySQL 8 기본 설정은 메모리를 많이 쓴다. 같은 박스에 데몬 3개 + 수집기가 이미
  돈다 → `innodb_buffer_pool_size`를 낮춰 잡고, systemd `MemoryMax`로 상한을 건다.
- 적재기는 **멱등**이어야 한다. 같은 JSONL을 두 번 적재해도 행이 두 배가 되면 안 된다
  (자연키에 unique index).
- 거래 평면 코드에서 DB 드라이버 import는 **아키텍처 위반**이다. 테스트로 막는다.

## 5. Phase 계획

Phase 1은 `main`에서. **Phase 2부터는 브랜치**(`redesign`)에서 진행하고, 확인 후 머지.
각 Phase 종료 시 커밋한다.

### ✅ Phase 1 — 저장소 통합 + 새 레이아웃 `main` (2026-08-13 완료)
`market_report`를 히스토리 보존하며 흡수(134커밋). 4평면 레이아웃으로 재배치.
`tests/test_architecture.py`가 임포트 그래프로 규칙 강제.
**결과:** 1,484 passed. 평면 위반 19건 → 5건(`KNOWN_DEBT`에 등재, 줄어들기만 함).
위반을 일부러 주입해 테스트가 실패하는 것까지 확인.

### ✅ Phase 2 — 트렌딩 점수에 매수세 반영 (완료)
하락률 보드 종목이 가점을 받는다 (CMG제약 55점). 롱 온리에서 폭락 종목에 점수를
주는 건 명백한 오류. 방향 필터를 먼저 적용.
**LLM 불필요. 다음 세션에 즉시 반영된다.**

### ✅ Phase 3 — MySQL 분석 저장소 + 적재 파이프라인 (완료) · Phase 3b Redis 계층 추가
§4의 스키마. 멱등 적재기. `forward_return` 채움.
**완료 기준:** "이 체결로 이어진 기사 목록"이 SQL 한 방으로 나온다.

### ✅ Phase 4 — 밀폐 백테스트를 적합도 함수로 (완료)
명령 하나, 네트워크 0, 비용·슬리피지 필수, 지표 묶음 반환, 룩어헤드 금지 테스트.
**이후 모든 자동 개선이 이 위에 선다. 여기가 거짓말하면 전부 무의미하다.**
우리는 이 함정의 구체적 형태를 이미 안다 — TQQQ 일중 엣지 8~9bp, 수수료 14bp.
비용을 빼고 최적화하면 하네스가 확실한 손실 전략을 최고점으로 들고 온다.

### Phase 5 — 감시 에이전트 상시 가동
EC2의 **Claude Code 예약 세션**(API 아님)으로 운영 이상 감지. 나중에 OpenRouter로
교체할 수 있도록 어댑터 경계를 둔다. 도구 권한 최소화.
감지 대상: 피드 죽음, 토큰 만료, 시계 어긋남, 시크릿 패턴, 원장 불일치.

### Phase 6 — OMS 주문 상태기계
`접수 → 부분체결 → 체결 / 거부 / 취소 / 만료`.
지금은 "주문했다"와 "체결됐다" 사이가 없다. paper에선 즉시 체결이라 안 보이지만,
실계좌에서 20주 중 8주만 채워지면 원장은 20주로 안다. **실거래 전환 선결 조건.**

### Phase 7 — Judgment 리더보드 + 섀도우 실행
```
Judgment { producer, producer_version, input_hash, output, ts }
```
`input_hash`가 핵심 — **같은 입력을 본 판단끼리만 비교할 수 있다.**
결정론적 스코어러가 베이스라인. LLM은 섀도우로 기록만 하고 실현 수익으로 채점되며,
**이겨야만 승격**한다. 못 이기면 안 넣으면 되고 비용은 0이다.

### Phase 8 — 개선 하네스
가설 → 밀폐 백테스트 → 채택. **시행 횟수 기록 필수** (deflated Sharpe).
에이전트가 쓴 코드는 브랜치 + CI + **사람이 머지**. 자동 머지 금지.

## 6. 강제되는 불변식

디렉토리가 아니라 **import 그래프가 아키텍처다.** 테스트로 강제한다.

| 규칙 | 막는 사고 |
|---|---|
| `core` → 아무것도 import 안 함 | 도메인 오염 |
| `trade` ↛ `collect`, `analyze` | 장중에 스크래핑하다 멈추는 것 |
| `analyze`, `collect` ↛ `trade` | **뉴스가 주문을 내는 것** |
| `control` ↛ `trade` | 자동 튜닝이 돌아가는 엔진을 건드리는 것 |
| `trade` ↛ DB 드라이버 | MySQL 장애가 매매를 멈추는 것 |
| 평면 간 통신은 `core.ports` 로만 | 숨은 결합 |

세 번째 줄이 §3에서 기각한 "뉴스 → 시그널 → 주문" 화살표를 코드 수준에서
불가능하게 만든다. 큐로는 못 하는 일이다 — 큐는 누가 뭘 발행하든 받아준다.

## 7. 이 계획을 결정한 측정값

추측이 아니라 실측이다. 다음 세션이 계획을 의심할 때 여기부터 본다.

| 측정 | 값 | 결론 |
|---|---|---|
| 체결 원장 (로컬) | 4거래일 35건, 최대 전략 왕복 12번 | **전략 자동 개선은 아직 근거가 없다.** Phase 8이 마지막인 이유 |
| 파이프라인 내 LLM | **0건** (임포트·엔드포인트 모두) | LLM은 의존성이 아니라 도전자. 리더보드가 옳은 설계 |
| 코드 규모 | 23,689줄 / 119모듈 / 테스트 1,507개 | 완전 재작성은 기각. 테스트가 이관 충실도를 증명한다 |
| TQQQ 일중 엣지 vs 수수료 | 8~9bp vs 14bp | 적합도 함수에 비용이 없으면 손실을 최적화한다 |
| RSS 9시간 뒤 재수집 | 주요 피드 겹침 **0**, 신규 153건 | 수집은 누적이어야 한다 (Phase 1 이전에 완료) |
| 이번 주 발견 결함 | 18개, 치명적 5개 | **5개 전부 사람이 발견.** 감시 자동화(Phase 5)가 시급한 이유 |

특히 마지막 줄:

| 결함 | 어떻게 발견됐나 |
|---|---|
| 키움 WS 토큰 20시간 죽음 | 사용자가 "중간중간 버그 걸리는 것 같다" |
| 알파벳 순서가 매수 종목 선정 | 사용자가 "왜 한화생명을 못 잡았지" |
| 08:40 데드라인 오판 | 위 조사 중 파생 |
| 타임존 9시간 오차 | 볼트 렌더 확인 중 |
| 텔레그램 토큰 381회 유출 | 로그 확인 중 |

알파벳 버그는 **시스템이 정상 작동하는 것처럼 보였다** — 주문이 나갔고 수익도 났다.
자동 감시로는 잡히지 않았을 종류이고, 그래서 사람이 체크포인트에 남아야 한다.
