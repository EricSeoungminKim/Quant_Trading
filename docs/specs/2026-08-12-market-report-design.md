# 개인 시황 리포트 시스템 — 설계

작성 2026-08-12 · 상태: 리뷰 대기

## 1. 목적

회사 데일리 리포트(`13.209.240.206:9999`) 의존을 끊고, 동등하거나 더 나은
개인 리포트를 **KR/US 두 종**으로 매일 자동 발행한다. 나아가 리포트가 낸 예측을
기록하고 실제 결과로 채점해, **시간이 갈수록 판단이 나아지는 구조**를 만든다.

핵심 요구 두 가지:

1. **재현 가능해야 한다** — 수집이 비결정론적이면 "어제 예측이 왜 틀렸나"를
   영원히 검증할 수 없다. 데이터 결측인지 판단 오류인지 구분되지 않기 때문이다.
2. **검증 가능해야 한다** — 예측은 산문이 아니라 반증 가능한 구조체여야 한다.

## 2. 비목표

- 실시간·장중 갱신 (하루 2회 발행으로 충분)
- 거래 주문 집행 (이 시스템은 주문을 내지 않는다)
- 회사 리포트의 보험사 뉴스 / 텔레그램 13채널 재현 (전자는 불필요, 후자는
  개인 구독 자산이라 재현 불가)
- 다중 사용자 / 인증 / 계정 (개인 전용, 공개 읽기)

## 3. 저장소 분리 근거

거래 저장소(`quant_trading_kiwoom`)와 **별도 저장소**로 만든다.

- 배포 시 리포트 박스에 거래 코드·시크릿이 존재할 이유가 없다. 공개 IP로
  노출되는 박스이므로 "털려도 나올 게 없다"를 저장소 경계로 보장한다.
- 의존성이 다르다 (브라우저 자동화, Jinja2, 유튜브 자막, LLM 클라이언트).
  거래 저장소 CLAUDE.md는 거래 엔진의 결정론성과 LLM 격리를 요구한다.
- 리포트 박스는 Toss API를 **쓸 수 없다** — Toss는 거래 EC2의 Elastic IP만
  화이트리스트하므로 새 IP에서는 403이다. 따라서 시세는 전부 공개 소스로 얻는다.
  이는 제약이 아니라 결합을 끊어주는 이점이다.

## 3.1 리포트의 성격 — 읽는 문서가 아니라 이중 산출물

회사 리포트는 **경영진이 읽기 좋게** 만든 문서다. 우리 것은 목적이 둘이다:

1. **엔진이 먹는 것** — 종목 후보 + 태그 + 근거가 기계 판독 형식으로 나온다.
   기존 파이프라인(`AUTO_WATCH: SYMBOL:TAG[+TAG][:YYYYMMDD]` → `watch-score`
   확신도 엔진 → 관심종목)과 **형식 호환**된다. 단 §11대로 **자동 연결은 아직 하지
   않는다** — 파일로 내보내기만 하고, 배선은 3층 채점이 유효성을 증명한 뒤다.
2. **사람이 코칭받는 것** — 지표를 짜깁기해 나열하는 대신 *"오늘 실제로 확인해야
   할 것"* 을 앞에 세운다. 다가오는 이벤트, 흐름이 바뀐 지점, 근거가 누적된 종목.

두 산출물은 **같은 구조체에서 생성된다.** 사람이 읽는 문장과 엔진이 먹는 토큰이
따로 놀면 리포트를 신뢰할 수 없다.

## 3.2 세션 윈도우 — "하루치"가 아니라 "직전 발행 이후"

리포트가 다루는 구간은 고정 24시간이 아니다. 월요일 KR 리포트는 **금요일 08:00
이후 ~ 월요일 08:00**까지, 즉 72시간을 다룬다. 공휴일이 끼면 더 길어진다.

**윈도우 시작점은 직전 스냅샷의 `generated_at`으로 정한다** (없으면 24시간 전).
요일 계산이나 공휴일 달력을 하드코딩하지 않는다 — 공휴일이든, 장애로 하루 걸렀든,
서버가 꺼져 있었든 자동으로 그 구간을 메운다. 자기 치유적이고 테스트하기 쉽다.

윈도우를 하루로 고정하면 **주말 뉴스가 통째로 사라진다.** 금요일 장 마감 후에
나온 재료가 월요일 시초가를 만드는데, 그걸 못 보는 리포트는 개장 전 리포트로서
쓸모가 없다.

## 3.3 연속성 — 어제를 버리지 않는다

수집물을 일회성으로 소비하지 않고 누적해, 리포트 안에 **흐름 칸**을 만든다.

| 계층 | 무엇을 쌓나 | 누가 계산하나 |
|---|---|---|
| 언급 원장 | 종목별 뉴스 등장 (날짜·출처·제목·링크) | **결정론적** — 종목 사전 매칭 |
| 연속성 지표 | N일 누적 언급, 연속 등장 일수, 신규 여부 | **결정론적** — 원장 집계 |
| 지표 델타 | 전 세션 대비 변화 (수급·유동성·VIX 등) | **결정론적** — 스냅샷 비교 |
| 호재/악재 판정 | 이 뉴스가 이 종목에 호재인가 | LLM (Phase 2) |
| 서술·코칭 | 흐름 해석, 매매 성격 분류 | LLM (Phase 2) |

> **핵심 원칙: 판정은 LLM이, 누적과 점수는 코드가.**
>
> "호재가 연달아 쌓이면 conviction이 오른다"를 LLM에게 맡기면 왜 그 점수가
> 나왔는지 설명할 수 없고, 3층에서 채점할 수도 없다. LLM은 **하루치 판정**만
> 하고, 며칠 연속인지 세고 가중치를 곱하는 건 결정론적 코드가 한다. 그래야
> 같은 원장에서 같은 conviction이 재현되고, 틀렸을 때 어느 단계가 틀렸는지
> 분리해서 추적할 수 있다.

Phase 1에서 언급 원장·연속성 지표·지표 델타까지 만든다 — **전부 LLM 없이 된다.**
종목 추천의 서술과 매매 성격 분류만 Phase 2로 남는다.

## 4. 아키텍처 — 4계층

| 층 | 역할 | 결정론 | 실패 영향 |
|---|---|---|---|
| 1 수집 | 스크레이핑 툴킷 → 버전 스냅샷 JSON | ✅ | 해당 섹션만 결측 |
| 2 판단 | 무료 LLM N개 병렬 → 구조체 예측 → 심판 합의 | ❌ | 그날 판단 누락, 데이터는 보존 |
| 3 채점 | 실제 결과 대조 → 모델별 원장 | ✅ | 채점 지연 |
| 4 정련 | 주 1회 하네스가 원장 기반 갱신 | ❌ | 없음 (오프라인) |

아래로 갈수록 실패 비용이 낮아지도록 배치했다. 실험적인 것일수록 발행 경로에서 멀다.

### 4.1 수집 (1층)

원칙: **API > JSON 엔드포인트 > 헤드리스 브라우저** 순서로 시도한다. 브라우저는
최후수단이다 (느리고, 깨지기 쉽고, 배포 박스에서 무겁다).

각 소스 모듈은 동일한 계약을 따른다:

```python
@dataclass(frozen=True)
class SourceResult:
    key: str            # "krx_investor_flow"
    ok: bool
    data: dict | None
    error: str | None
    url: str            # 출처 (리포트에 그대로 렌더)
    fetched_at: datetime
    latency_ms: int
```

**한 소스의 실패가 리포트를 죽이지 않는다.** 실패한 섹션은 HTML에 "결측 —
사유"로 표시되고, 스냅샷에도 `ok: false`로 남는다. 결측을 조용히 숨기면 3층
채점이 오염된다.

스냅샷은 `data/snapshots/{market}/{YYYY-MM-DD}.json`에 스키마 버전과 함께 쓴다.
**같은 스냅샷으로 리포트를 재생성하면 항상 같은 결과가 나와야 한다** (LLM 층 제외).

### 4.2 판단 (2층)

무료 모델 N개가 **각자 독립적으로** 같은 스냅샷을 보고 구조체를 낸다:

```json
{
  "market": "KR",
  "horizon": "1d",
  "direction": "up | down | flat",
  "confidence": 0.72,
  "key_drivers": ["외국인 3일 연속 순매수", "VIX 백워데이션 해소"],
  "invalidation": "달러/원 1,400 상향 돌파 시 무효",
  "candidates": [{"symbol": "005930", "thesis_tag": "SUPPLY", "conviction": 0.6}]
}
```

`confidence`와 `invalidation`이 필수인 이유는 3층이 채점하기 위해서다. 이 필드가
없으면 예측이 반증 불가능해지고 시스템 전체의 목적이 사라진다.

심판 모델이 N개 구조체를 받아 합의본을 만들되, **개별 모델 예측은 전부 원장에
따로 남긴다** — 모델별 성적을 재려면 합의 전 원본이 필요하다.

사람이 읽는 HTML 산문은 이 구조체와 스냅샷에서 **생성된다.** 역방향이 아니다.

### 4.3 채점 (3층)

다음 세션에 실제 결과를 공개 소스로 긁어 전날 예측을 채점한다.

- **방향 적중률** — direction vs 실제 지수 등락
- **Brier score** — `(confidence - outcome)²`, 확신도 보정 품질
- **후보 종목 전방 수익률** — 추천 종목의 1일/5일 실제 수익률
- **결측 상관** — 어떤 섹션이 빠졌을 때 예측이 나빠지는가 (소스 우선순위 근거)

모델별로 `data/ledger/forecasts.jsonl`에 적립. `report model-scoreboard`로 집계.
거래 저장소가 전략에 하는 일(`trades.jsonl` → `run scoreboard`)을 모델에 한다.
**숫자가 모델 로스터를 결정한다.**

### 4.4 정련 (4층)

주 1회, 하네스(prime-agent 또는 Claude Code)가 누적 원장을 읽고 프롬프트·소스
가중치·모델 로스터 갱신을 제안한다. 일일 발행 경로 **바깥**에서 돌므로 실패해도
리포트가 멈추지 않는다. Phase 4에서 착수하며, 1~3층은 하네스 중립적으로 만든다.

## 5. 소스 카탈로그 (2026-08-12 실측)

실제로 찔러본 결과다. 난이도 분류가 곧 Phase 1 작업 계획이다.

### ✅ 즉시 가능 (키 불필요, 검증 완료)

| 소스 | 얻는 것 | 확인 |

| yfinance | 지수·환율·원자재·VIX·DXY·국채·섹터ETF·크립토·K200 | 10종 일괄 조회 성공 |
| yfinance 옵션체인 | SPY/QQQ **P/C비율·MaxPain 자체 계산** | SPY 33개 만기, vol P/C 1.131 산출 |
| YouTube RSS | 채널별 최신 영상 (제목·링크·시각) | Damodaran 15건 |
| CFTC COT | 투기·헤저 포지션 | `publicreporting.cftc.gov` 200 |
| Atlanta Fed GDPNow | GDP 나우캐스트 시계열 | xlsx 48KB |
| FRED `fredgraph.csv` | WALCL·TGA·RRP → **순유동성**, NFCI, 국채금리 | WALCL 최신 2026-08-05 |

(HTTP/2, IPv6) 이슈다. 구현 시 클라이언트 옵션을 맞춘다.

### 🔧 스크레이핑 작업 필요 (Phase 1의 실제 난이도)

| 소스 | 상태 | 대응 |
|---|---|---|
| ~~KRX 투자자 수급~~ | **해결** — 아래 참조 | 네이버금융 확정 |
| CME FedWatch | 403 | Investing.com Fed Rate Monitor(회사 리포트가 쓰는 경로) 또는 브라우저 |
| Investing 경제캘린더 | JS 렌더링, 403 | **불필요해짐** — FRED `releases/dates`로 대체(§5.1) |
| 금투협 FREESIS | 예탁금·신용융자 | 미검증 |
| 한국 CDS·VKOSPI | KRX 파생 계열 | 미해결 |

**투자자 수급 — 네이버금융으로 확정 (2026-08-12 실측).**
`data.krx.co.kr`이 `400 LOGOUT`으로 막혀 있어 최대 리스크로 봤으나, 회사 리포트의
`source` 필드를 역추적하니 그쪽도 KRX가 아니라 `naver_finance`를 쓰고 있었다.
동일 경로가 열린다:

```
GET https://finance.naver.com/sise/investorDealTrendDay.naver?bizdate=YYYYMMDD&sosok={01|02}
     sosok=01 → KOSPI, 02 → KOSDAQ. euc-kr 인코딩.
```

주체별 전부 나온다: 개인 · 외국인 · 기관계 · 기타법인 · 금융투자 · 보험 ·
투신(사모) · 은행 · 기타금융기관 · 연기금등.

> **주의 — 컬럼 매핑을 검증 없이 신뢰하지 않는다.** 실측에서 `<th>` 12개 대 데이터
> 셀 11개로 어긋난다(`기관계`/`기관`이 colspan 그룹 헤더로 보인다). 컬럼을 밀려
> 읽으면 "외국인 순매수"가 조용히 틀린 값이 되고, 그건 KR 리포트에서 가장 중요한
> 숫자다. Phase 1에서 **네이버 화면 표시값과 대조하는 테스트를 반드시 넣는다.**

따라서 `KRX_API_KEY`는 불필요하다 — 발급받지 않는다.

### ❌ 제외

텔레그램 13채널(개인 구독, 재현 불가), 보험사 뉴스(용도 없음).

### 참고 — 회사 리포트의 실제 데이터 출처

`source` 필드를 전수 조사한 결과(2026-08-12), 회사 리포트의 시세·지표는 대부분
**유료 벤더**에서 온다:

| 그쪽 출처 | 쓰는 곳 | 우리 대응 |
|---|---|---|
| **EODHD** (유료 API) | VIX 기간구조, 글로벌 뉴스, S&P 가격 | yfinance + RSS |
| **Infomax xlsx** (연합인포맥스, 유료) | 야간 K200·NDF·채권 | yfinance + 공개 소스 |
| `tradingview_playwright` | S&P 신고가/신저가 | 구성종목 직접 계산 |
| `naver_finance` | KRX 투자자 수급 | **동일 경로 사용** |
| Investing.com Fed Rate Monitor | FedWatch | 동일 경로 검토 |

`finance.yahoo.com`은 그쪽에서 **뉴스 소스로만 5곳** 등장하고 시세용이 아니다.
즉 우리는 그들과 정반대로 **yfinance를 시세 백본으로 삼는다** — 유료 벤더를 쓸 수
없으니 불가피한 선택이다.

**그에 따르는 리스크와 완화책:** yfinance는 야후의 비공식 스크레이퍼라 야후가
엔드포인트를 바꾸면 깨진다(과거 여러 차례 발생). 단일 벤더 의존이 이 시스템의
가장 큰 구조적 취약점이므로 셋으로 방어한다:

1. **격리** — `SourceResult` 계약상 yfinance가 죽어도 해당 섹션만 결측이 된다.
2. **교차검증** — 핵심 시계열(KOSPI·S&P·달러/원·VIX)은 **2차 무료 소스**(Stooq,
   FRED, 네이버금융)로 한 번 더 받아 괴리가 임계 초과면 리포트에 경고를 띄운다.
   조용히 틀린 숫자보다 시끄럽게 결측인 편이 낫다.
3. **스냅샷** — 매 실행분이 보존되므로 값이 튀거나 끊긴 시점이 즉시 드러난다.

## 5.1 이벤트 캘린더 (예정일 선행 정리)

CPI·FOMC 같은 이벤트는 **터진 뒤 요약보다 터지기 전 예고가 훨씬 유용하다.**
리포트 상단에 향후 14일 고영향 이벤트를 D-day와 함께 고정 배치한다.

**스크레이핑하지 않는다.** Investing.com 경제캘린더(403)와 BLS 공표일정(403)은
둘 다 봇을 차단하는데, 같은 정보를 공식 API가 제공하기 때문이다:

| 이벤트 | 소스 | 확인 |
|---|---|---|
| CPI·PPI·고용·PCE·GDP·소매판매 등 미 지표 발표일 | **FRED `/fred/releases/dates`** (무료 키) | 엔드포인트 도달, 키 미설정 400 |
| FOMC 회의·의사록·SEP | **federalreserve.gov 공식 캘린더** | 200, 164KB 파싱 가능 |
| 원유 재고 발표 | EIA (무료 키) | 키 필요 |
| 개별 종목 실적 | yfinance `get_earnings_dates` | `lxml` 의존 추가 필요 |
| 한국 지표·금통위 | 한국은행 보도자료 일정 | 200 (경로 확정 필요) |

FRED 릴리즈 계열은 발표일뿐 아니라 **직전값·컨센서스 부재 시 과거 시계열**을 같이
주므로, "이번 CPI는 전월 대비 어디서 출발하는가"를 자동으로 붙일 수 있다.

렌더링 규칙:

- 향후 14일 이벤트를 KST로 변환해 D-day 순 정렬 (`CPI D-3`, `FOMC D-12`)
- 고영향(FOMC·CPI·고용·PCE)은 시각 강조, 당일/익일 이벤트는 최상단 고정
- **US 서머타임 전환을 반영해 ET→KST 변환**한다 (거래 저장소가 겪은 고정 크론
  DST 사고와 같은 실수를 반복하지 않는다)

2층 연계: 예측 horizon 안에 고영향 이벤트가 있으면 그 사실을 프롬프트에 명시하고,
**이벤트 전날의 방향 예측은 confidence 상한을 두거나 별도 태깅**한다. 3층 채점에서
"이벤트 낀 날 예측"과 "평범한 날 예측"의 성적을 분리해 봐야 모델 평가가 왜곡되지
않는다.

## 5.2 원자재 흐름

가격만으로는 "흐름"이 안 보이므로 세 축을 함께 싣는다.

| 축 | 소스 | 확인 |
|---|---|---|
| 가격·추세 | yfinance — 금·은·구리·WTI·브렌트·천연가스·밀·옥수수·대두 | 일괄 조회 성공 |
| 포지셔닝 | **CFTC COT 투기적 순포지션** | `publicreporting.cftc.gov` 200 |
| 재고 | EIA 원유 재고 (무료 키) | 키 필요 |

여기에 **자체 계산 파생 지표**를 얹는다 — 원자료만 나열하는 회사 리포트와
차별화되는 지점이다:

- **금/구리 비율** — 경기 기대의 대용치 (구리 강세 = 경기 확장)
- **브렌트−WTI 스프레드** — 지역 공급 병목
- 각 원자재의 **COT 순포지션 백분위** (최근 3년 대비 현재가 몇 분위인가) —
  절대 계약수보다 극단 여부가 신호다

## 7. 발행

- 정적 HTML. Jinja2 템플릿. 외부 CDN 의존 없음(오프라인에서도 열림).
- 경로: `out/{YYYY}/{MM}/{DD}/{market}_report_{HHMMSS}.html` + 같은 이름 `.json`
- 스냅샷 원본도 함께 보관해 재생성 가능성을 유지한다.
- 로컬 검증 단계에서는 `python -m quant.apps.report_cli serve`로 로컬 확인만 한다.

## 8. 비용

| 항목 | 비용 |
|---|---|
| OpenRouter | **$10 일회성** — `:free` 모델은 토큰 단가 0이라 크레딧이 차감되지 않는다. $10은 50 req/day → 1,000 req/day 상한 해제용이다 |
| 서버 | Phase 5에서 결정 (OCI Always Free = 0원 / EC2 = 월 $10~15) |
| 데이터 | 0원 (전부 무료 소스) |

일일 호출 추정: 리포트당 섹션요약 ~8 + 판단모델 4 + 심판 1 ≈ 13, ×2 = **~26콜**.
50/day에서도 돌지만 재시도 여유가 없다. 개발 중 프롬프트 반복이 가장 호출을 많이
먹으므로, Phase 2 착수 시점에 $10을 넣는 것을 권한다.

무료 모델은 현재 **16종**뿐이고 대부분 소형이다 (nemotron-3-ultra-550b 1M ctx,
nemotron-3.5-lightning 1M, gemma-4-31b 262K, gpt-oss-20b 131K 등). 요약·추출에는
충분하나 **시황 판단 품질은 미지수다.** 이것이 3층 채점이 존재하는 이유다 —
쓸모없으면 몇 주 안에 숫자가 말해준다. 그때 남은 크레딧으로 유료 모델을
벤치마크로 붙여 격차를 잰다.

## 9. 보안 (배포 시)

- API 키는 웹루트 밖 `0600`, 별도 유닉스 유저 소유.
- 정적 서버 루트는 **`out/` 디렉토리만.** 저장소 루트에서 `python -m http.server`
  금지 — 회사 리포트가 디렉토리 리스팅이 열려 있어 파일명 규칙이 그대로 노출된다.
- 리포트 박스에는 거래 시크릿·거래 코드 없음 (§3).
- 키를 쓰는 프로세스는 아웃바운드 전용. 인바운드 서비스는 정적 파일만 서빙.

## 10. 단계

| Phase | 내용 | 완료 기준 |
|---|---|---|
| **1** | 스크레이핑 툴킷 + 스냅샷 + HTML (LLM 0) | KR/US 리포트가 로컬에서 생성되고, 같은 스냅샷 재생성이 동일 결과 |
| 2 | 멀티모델 판단 + 구조체 예측 | 예측 JSON이 원장에 적립 |
| 3 | 채점 + `model-scoreboard` | 모델별 적중률·Brier 산출 |
| 4 | 하네스 정련 루프 | 원장 근거 갱신 제안 |
| 5 | 서버 배포 (OCI 또는 EC2) + 크론 | 정해진 시각 자동 발행 |

**Phase 1~4는 전부 로컬에서 검증한다.** 사용자가 리포트 품질에 만족한 뒤에만
Phase 5로 간다.

### Phase 1 로컬 검증 기준

같은 날짜의 회사 리포트와 나란히 놓고 판단한다:

1. **커버리지** — 회사 리포트 섹션 중 빠진 게 무엇이고 그게 아쉬운가
2. **정확성** — 숫자 5~10개를 원 출처와 대조해 일치하는가
3. **가독성** — 5분 안에 오늘 시장을 파악할 수 있는가
4. **차별성** — 회사 리포트에 없는데 유용한 게 있는가 (자체 계산 MaxPain, 순유동성 등)
5. **재현성** — 같은 스냅샷으로 두 번 생성해 결과가 동일한가

## 10.1 발행 시각 — 양쪽 모두 개장 60분 전 (확정)

| 리포트 | 개장 | 발행 | 비고 |
|---|---|---|---|
| KR | 09:00 KST | **08:00 KST** | 전일 KRX 수급 확정, 미국장 마감(05:00~06:00 KST) 이후라 야간 데이터가 모두 갖춰진다 |
| US | 09:30 ET | **08:30 ET** = 21:30 KST(EDT) / 22:30 KST(EST) | DST 자동 추종 |

**DST는 고정 KST 시각으로 하드코딩하지 않는다.** 스케줄은 항상 `America/New_York`
기준 08:30에서 KST로 환산해 계산한다 — 거래 저장소가 겪은 고정 크론 DST 사고
(동계에 하루 늦게 실행)를 반복하지 않기 위해서다. 로컬 검증 단계에서는 크론 없이
CLI로 수동 실행하므로 이 규칙은 스케줄 코드가 아니라 **시각 계산 유틸과 그 테스트**로
먼저 구현한다.

## 11. 미결

- **엔진 연결** — 3층 스코어보드가 무료 모델 판단의 유효성을 증명하기 전까지는
  거래 엔진 관심종목에 연결하지 않는다. 연결 시에도 기존 `watch-score` 확신도
  엔진을 반드시 경유한다.
- **호스팅** — Phase 5에서 결정. OCI Always Free는 2026-06-15부로 2 OCPU/12GB로
  축소됐고 초과 인스턴스는 2026-08-18 종료 예정이므로, 그 전에 기존 인스턴스
  상태 확인이 필요하다.
