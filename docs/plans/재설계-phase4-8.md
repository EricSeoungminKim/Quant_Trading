## ✅ Phase 4 — 밀폐 백테스트를 적합도 함수로 (2026-08-13 완료)

**왜 이게 다음인가.** Phase 8 하네스가 최적화할 대상이다. **적합도 함수가
거짓말하면 그 위에 쌓은 자동 개선이 전부 조용히 틀린다.** 우리는 이 함정의
구체적 형태를 안다 — TQQQ 일중 엣지 8~9bp vs 수수료 14bp. 비용을 빼고
최적화하면 하네스가 확실한 손실 전략을 최고점으로 들고 온다.

- [x] **4.1 DuckDB 도입** — `quant/adapters/olap.py`. Parquet 을 그대로 테이블로
      읽는다(적재 단계 없음). `quant.trade` 의 duckdb 임포트는 이미 아키텍처
      테스트가 막고 있다.
      - 검증: `SELECT count(*) FROM read_parquet('data/history/**/*.parquet')`
- [x] **4.2 비용 모델을 명시 파라미터로** — 수수료·세금·슬리피지가 `config` 한
      곳에 모이고, 백테스트가 **반드시** 읽는다. 기본값 0 을 허용하지 않는다
      (0 을 허용하면 언젠가 0 으로 돌고 아무도 모른다).
      - 검증: 비용 0 으로 돌리려 하면 실패하는 테스트
- [x] **4.3 룩어헤드 금지 강제** — `HistoryDataFeed` 의 완성봉 규칙을 백테스트
      경로 전체에 대해 테스트한다. 하네스가 가장 먼저 찾아낼 구멍이다.
      - 검증: 미래 봉을 요청하면 빈 결과가 나오는 테스트
- [x] **4.4 지표 묶음 반환** — 승률·payoff·MDD·**명목 대비 bps**·표본수.
      명목 대비 bps 가 핵심이다(총수익률은 계좌 크기에 오염된다).
- [x] **4.5 밀폐성** — 네트워크 호출 0. `--offline` 이 기본.
      - 검증: 소켓을 막고 돌려도 통과하는 테스트
- [x] **4.6 한 명령** — `quant.apps.cli fitness --strategy X --from A --to B`
      가 JSON 지표를 stdout 으로 낸다. 에이전트가 부를 수 있어야 한다.

> 🔴 **이 phase 가 남긴 구멍 (2026-08-15 원장으로 확인)**: 비용 모델이 **백테스트에만**
> 있고 **라이브 진입 판단에는 없다.** 전략은 신호만 보고 진입하므로, 백테스트가 비용
> 때문에 기각할 거래를 라이브는 그대로 낸다. 실측 결과 US 3개 전략이 **전부 수수료 전
> 양수인데 왕복 20bp 가 전부 음수로 뒤집었다.** 상세: [`개선-백로그-2026-08-15.md`](개선-백로그-2026-08-15.md) §1.

## ✅ Phase 5 — 감시 에이전트 + 백업 (2026-08-13 코드 완료, 배포 대기)

**왜.** 이번 주 치명적 결함 5개를 **전부 사람이 발견했다.** 그중 넷(토큰 만료,
데드라인 오판, 타임존, 시크릿 패턴)은 자동 감시가 잡을 수 있는 종류였다.
그리고 **백업이 없다** — 아티팩트가 진실인데 EC2 디스크 한 곳에만 있다.

> **배포되지 않으면 이 phase 는 아무것도 감시하지 않는다.** 크론 4개(백필·백업·
> 리허설·감시)가 저장소에만 있다. 설치 절차는 `docs/runbooks/deploy.md` 와
> 아래 "남은 것".

      EC2 에 AWS 자격증명이 없고(IAM 은 미결 사용자 작업), 더 중요하게는 **EC2 가
      털렸을 때 백업까지 지울 수 있는 키를 같은 박스에 두지 않으려는** 것이다.

### 배포하니 감시가 잡은 것 (전부 진짜 · 아무도 모르고 있었다)

1. **뉴스 수집이 오후마다 죽고 있었다** — `TimeoutStartSec=300` 이 `CPUQuota=30%` 와
   모순(CPU 1분29초 → 월클럭 최소 5분). 그날 KR 성공 6 / 타임아웃 실패 10.
   SIGTERM 으로 죽으면 그 회차 RSS 기사가 **영구 소실**된다. 900 으로 고쳤고 이후
   실행이 `Result=success`(CPU 2분21초).
2. **계측이 조용히 사라지고 있었다** — 유닛에 `EnvironmentFile` 이 없어 `REDIS_URL`
   을 못 보고 `make_kv()` 가 `NullKeyValue` 를 돌려줬다. 호출은 있고 효과는 없는
   "적용했다고 믿기" 패턴.
3. **`HEARTBEAT_TTL` 이 자기 주석과 모순** — "30분 주기가 한 번 걸러도 살아있다"면서
   값이 15분이라, 정상인 30분 작업도 매 주기 후반은 "최근 성공 없음"이었다 → 3600.
4. **설정에서 빠진 피드를 죽은 피드로 경보** — `연합뉴스`·`한경` 은 이름 개편으로
   사라진 것인데 zset 에 옛 이름이 남아 영구 거짓 경보가 됐다 → 로스터 주입 필터.

## ✅ Phase 6 — OMS 주문 상태기계 (2026-08-14 완료, 배포 대기)

**왜.** 실거래 전환 선결 조건. 지금은 "주문했다"와 "체결됐다" 사이가 없다.
paper 는 즉시 체결이라 안 보이지만, 실계좌에서 20주 중 8주만 채워지면 원장은
20주로 안다.

- [x] **6.1 `core/models.py` 에 `Order` 상태** — `OrderStatus`/`OrderState`.
      어휘를 지어내지 않았다 — 토스가 실제로 돌려주는 값에서 가져왔다.
      **"모른다"를 상태로 만들지 않는다**: 결론 없이 끝난 주문은 그냥 *열린 채*다.
- [x] **6.2 순수 상태기계** — **`quant/core/oms.py`** (계획서는 `trade/` 라고 했다).
      어댑터가 이걸 써야 하는데 `quant.adapters` 는 `quant.trade` 를 임포트할 수
      없다 — 두 평면이 같은 전이 규칙을 쓰려면 의존 방향의 바닥에 있어야 한다.
- [x] **6.3 `Broker` Protocol 확장** — `place_order` 가 `OrderState` 를 반환.
      거부/미제출/결론없음/부분체결이 `None` 하나로 뭉개지지 않는다.
      구분은 상태를 늘리지 않고 `broker_order_id is None` 으로 한다.
      어댑터는 `oms.report_fill`(예외를 삼키는 변형)을 쓴다 — 구현 중 상태기계
      예외가 루프까지 올라가 **이미 일어난 체결이 버려지는** 일이 실제로 났다.
- [x] **6.4 원장에 주문 생애 기록** — `data/state/orders.jsonl`(체결 원장과 분리).
      **6.3 보다 먼저 했다**: 부분 체결 정보는 `fill.qty` vs `order.qty` 로 이미
      존재했고, Protocol 을 안 바꾸고도 잔량을 남길 수 있었다.
- [x] **6.5 대사 확장** — `OpenOrderBook` 이 미체결 잔량을 들고, 대사가 그걸로
      "사용자 수동 보유"와 "**우리 주문의 늦은 체결**"을 가른다. 후자는 엔진이 자기
      포지션을 모르는 상태라 정보성 로그로 묻히면 안 된다.
      장부에 **TTL(60분)이 있다** — 없으면 열린 채 남은 주문이 영원히 잔량으로 남아
      영구 halt 생성기가 된다(구현 중 실제로 만든 결함).

### 남은 것

- [x] **EC2 배포** (2026-08-14) — 리부팅 후 데몬 5개 자동 복구, 엔진 에러 0.

## 🔸 Phase 7 — Judgment 리더보드 + 섀도우 (2026-08-14 배선 완료 · **입력이 아직 없다**)

> **결론을 먼저**: 기계는 다 돌아가고 실환경에서 검증됐다. 그런데 **리더보드가 아직
> 아무 말도 할 수 없다** — 결정론적 베이스라인의 점수가 거의 상수라서 순위가 만들어
> 지지 않는다. 그게 고장이 아니라 정직한 상태이고, 다음 할 일은 Phase 7 배관이
> 아니라 **입력을 쓸 수 있게 만드는 것**이다.
>
> 실측(2026-08-14, EC2):
> - 판단 254건 · 서로 다른 `input_hash` 40개 · score 있는 판단 62건
> - **그 62건 중 59건이 점수 50** — `trending_score.py` 가 "근거 없음"에 쓰는 중립값이다
>   (그 파일 주석: "근거 없음과 근거가 나쁨을 섞지 않기 위해 50을 중립으로 쓴다").
>   즉 베이스라인 판단의 **95%가 정보를 담고 있지 않다.**
> - 기준가(`close`)가 있는 행이 178행 중 15행 — 리포트가 시세를 **랭킹·매핑된 종목만**
>   받아오기 때문이다. 채점 가능(기준가+점수) 교집합은 하루 **5종목**.
> - 그래서 `ic_by_day: {"2026-08-14": null}` — 순위 상관이 계산되지 않는다.
>   리더보드는 `insufficient_sample`(거래일 0일)을 낸다. **정확한 답이다.**
>
> **다음 할 일(Phase 7 를 쓸 수 있게 만드는 것):**
> 1. 리포트가 **올린 종목 전부의 기준가**를 남기게 한다(지금은 일부만). 이게 없으면
>    표본이 하루 5개고, 5종목 횡단면 IC 는 잡음이 신호보다 크다.
> 2. `trending_score` 가 랭킹 보드 밖 종목을 전부 50 으로 두는 것을 재검토한다 —
>    베이스라인이 상수면 LLM 이 "이기는" 것이 무의미하다(아무거나 이긴다).
> 3. 그 둘이 되면 20거래일을 모아 처음으로 판정을 낸다.

**왜.** LLM 을 "도입"하는 게 아니라 **채점**하는 구조. 결정론적 스코어러가
베이스라인이고, LLM 은 이겨야만 승격된다. 못 이기면 안 넣으면 되고 비용은 0.

- [x] **7.1 `judgment` 테이블 + `input_hash`** — `002_judgment.sql`, 멱등 적재.
      해시에 **생산자도 출력도 넣지 않는다** — 넣으면 같은 입력을 본 두 판단이 다른
      해시를 갖고 비교가 불가능해진다. 실측 검증: 40개 해시(구현 초기엔 1개였다).
- [x] **7.2 forward_return 채움** — `cli outcomes`(매일 16:00). 과거 시세 조회 대신
      **그날 만기가 된 지평만** 채운다(오늘 종가만 필요). 실측: 10건 채움.
      평일 근사를 쓰므로 실제 기준일(`asof`)을 함께 남긴다.
- [x] **7.3 결정론적 베이스라인 기록** — `selection_judgment()`. selections 를 다시
      만들지 않았다(이미 속성 벡터를 남긴다) — 더한 건 생산자 귀속과 해시뿐이다.
- [x] **7.4 섀도우 실행** — `cli shadow-judge`. **주문을 내지 않는다.** 프롬프트에
      `is_candidate`·점수를 넣지 않는다(보여주면 베끼기만 해도 이긴다). 형식 위반·
      범위 밖·목록 밖 종목은 버린다 — 0점을 주면 "최하위 평가"가 되어 IC 를 오염시킨다.
- [x] **7.5 승격 규칙** — `control/leaderboard.py`. **표본을 판단 수가 아니라 거래일
      수로 센다** — 같은 날 종목들은 시장 움직임을 공유해 독립 관측이 아니고, n=199 로
      세면 거의 무엇이든 유의해진다. 단위는 하루의 횡단면 순위 IC.
      문턱 20거래일의 근거: IC sd≈0.12, 탐지 대상 IC 0.05, t=2 → n≈23.
      다중검정 Bonferroni 로 요구 t 를 올린다. **자동 적용하지 않는다**(판정만).
