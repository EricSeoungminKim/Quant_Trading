# 테마 기반 종목 탐색 (서브프로젝트 F) — 설계 스펙

> 2026-08-15. 사용자 요구: *"한국장 섹터마다 대장주가 네이버 증권에 데이터로 있다.
> 뉴스와 종목 기반으로 관련 수혜주를 **추측 말고 팩트 기반**으로, 부품이 수혜라면
> **어떤 부품·섹터인지**까지. 막무가내로 삼성·하이닉스만 하는 게 아니다."*
>
> A(뉴스 심화)의 KR 경로를 대체·보강한다. B(리포트 UI)의 테마 섹션이 이걸 소비한다.

## 무엇이 바뀌는가 — A 의 한계

A 의 관계 추출은 **LLM 이 후보를 만들고** 뉴스 코퍼스가 검증하는 구조다. 두 약점:

1. **소스 선정이 언급 수 상위 10종목** — 대형주가 뉴스를 독점하므로 매일
   삼성전자·SK하이닉스만 파게 된다(사용자 지적 그대로).
2. **"왜 수혜주인가"를 LLM 이 쓴다** — 그럴듯하지만 출처가 없다.

## 핵심 발견 (2026-08-15 실측)

네이버 테마 페이지가 **사람이 큐레이션한 팩트**를 이미 갖고 있다:

- 테마 목록: `finance.naver.com/sise/theme.naver` (페이지당 40개, 페이지네이션)
- 테마 상세: `sise_group_detail.naver?type=theme&no=N`
- **각 소속 종목에 "테마 편입 사유"가 붙는다**:
  - `GS` → *"정유업체 GS칼텍스를 손자회사로 보유"*
  - `SK이노베이션` → *"SK그룹 계열의 종합에너지기업으로 100% 자회사인 SK에너지를 통해 정유사업을 영위"*
- 같은 행에 현재가·등락률·거래량·**거래대금**이 있다(업종 상세와 동일 레이아웃).

즉 **"어떤 종목이 왜 이 테마에 속하는가"가 출처 있는 사실로 존재한다.**
LLM 이 지어낼 필요가 없다.

## 설계 — 팩트 앵커 + 뉴스 증거

```
뉴스 → (기존 매칭) 종목 코드
        ↓  종목 → 소속 테마들           [팩트: 네이버 테마 멤버십]
        ↓  테마 → 같은 테마의 다른 종목  [팩트: 수혜주 후보군]
        ↓  각 후보의 "편입 사유"          [팩트: 왜 수혜주인가 — 출처 있음]
        ↓  뉴스 코퍼스 증거 점수          [기존 evidence_score 재사용]
        → 관계 사전
```

- **관계의 근거가 LLM 문장이 아니라 네이버 편입사유**가 된다. `reason` 의 출처를
  `source: "naver_theme"` 로 명시해 LLM 산 `reason` 과 구분한다(둘을 섞으면
  나중에 품질을 가릴 수 없다).
- **"어떤 부품·섹터인가"** = 테마명 그 자체(`HBM`, `2차전지(생산)`, `정유`).
  관계 행에 `via_theme` 를 남긴다.
- LLM 은 **선택**으로 남는다: 테마 밖 관계(신규 공급 계약 등)를 제안할 때만.
  죽어도 테마 기반 관계는 그대로 나온다.

## 소스 선정 — 대장주 + 섹터 균형

언급 수 상위 10 대신:

1. **뉴스가 가리키는 테마**를 먼저 고른다(그날 기사에서 매칭된 종목들의 소속 테마를
   집계 — 테마 단위로 세면 대형주 편중이 줄어든다).
2. 각 테마에서 **그날의 대장주**를 고른다 — 기준은 **거래대금**(테마 상세가 준다).
   시가총액은 이 페이지에 없다; 거래대금이 "오늘 돈이 몰린 종목"이라 뉴스 기반
   단타 관점에 더 맞다. **시총 기준이 필요하면 별도 소스가 필요하다는 사실을 명시**한다.
3. 테마당 상한을 두어(예: 테마 2개 × 종목 N) 한 테마가 전체를 먹지 않게 한다.

이렇게 하면 "삼성·하이닉스만"이 구조적으로 불가능해진다 — 반도체 테마는 한 자리를
차지할 뿐이다.

## 구성요소

| 구성요소 | 평면 | 파일 | 역할 |
|---|---|---|---|
| 테마 수집 | collect | `quant/collect/sources/naver_theme.py` (신규) | 테마 목록(페이지네이션) + 상세(종목·**편입사유**·등락·거래대금) 파싱·수집 |
| 테마 사전 | control | `data/ledger/themes.json` | `{theme_no: {name, symbols: [{code, name, reason, value_traded}]}}` 아티팩트 |
| 탐색 로직 | analyze | `quant/analyze/theme_search.py` (신규, 순수) | 뉴스 매칭 → 테마 집계 → 대장주 선정 → 수혜주 후보 + 근거 |
| deepdive 통합 | apps | `quant/apps/deepdive.py` (수정) | KR 경로에서 테마 기반 소스 선정·관계 생성. US 는 기존 LLM 경로 유지 |
| 스키마 | adapters | `003_relations.sql` 확장 또는 신규 | `relation` 에 `via_theme`·`source` 컬럼 |

## 관계 행 스키마 확장

```
{src, dst, kind, reason, evidence_score, first_seen, last_verified,
 via_theme: str|None,        # 어떤 테마를 통해 연결됐나 (= 어떤 부품·섹터)
 source: "naver_theme"|"llm" # 근거의 출처 — 섞지 않는다
}
```

기존 소비자(B 트리, engine JSON)는 새 키를 **있을 때만** 읽는다(A·E 와 같은 관례).

## 비목표

- 시가총액 기준 대장주(이 페이지에 없다 — 필요하면 별도 스펙)
- US 시장(테마 데이터가 없다 — 기존 LLM 경로 유지)
- 테마 자동 생성·수정(네이버가 주는 것을 그대로 쓴다)
- 전략·주문 로직 변경(거래 평면 무접촉)

## 실패 모드

| 실패 | 동작 |
|---|---|
| 테마 목록/상세 실패 | 어제 `themes.json` 으로 진행. 그것도 없으면 **A 의 기존 LLM 경로로 폴백**(리포트는 계속 나간다) |
| 편입사유 없는 종목 | 그 종목은 후보에서 제외(빈 이유로 관계를 만들지 않는다) |
| 테마에 종목 1개뿐 | 수혜주 후보가 없으므로 건너뜀 |
| 수집이 느림(테마 수백 개) | 일 1회 야간 배치 + 캐시. 리포트 발행 경로에서는 아티팩트만 읽는다 |

## 검증

- 파서: **실 HTML 조각** 픽스처(편입사유가 있는 행 / 없는 행 / 페이지네이션 끝)
- 탐색 로직: 순수 함수 단위 테스트 — 특히 **한 테마 독식 방지 상한**과
  "삼성전자만 10개" 같은 결과가 나오지 않음을 고정
- E2E(EC2): 실행 후 `themes.json` 종목 수, 관계 중 `source=naver_theme` 비율,
  소스로 뽑힌 종목의 **테마 분산**을 직접 센다
