# Spark 보고서 평가 — 2026-09-14

**결정: 무검수 자동발행용 Spark 전면 전환은 채택하지 않는다.** 실제 KR 보고서
빌드와 모든 관찰 Codex 호출은 성공했지만, 자동 검사를 통과한 응답에도 의미와
표현 문제가 남았다. 이 평가는 운영 기본 모델 변경을 포함하지 않는다.
전역 `CODEX_MODEL`, Telegram 브리지, AI 트레이더, 거래 설정은 유지한다.

## 검증 자료와 범위

수치의 근거는 EC2 실응답을 보존한 JSON이다. 최초 작업 사본은
`/tmp/qt-spark-evidence`, 재현 자료의 보존 위치는
`data/acceptance/spark-report-2026-09-14/`이다. 후자는 git 미추적이며
`.gitignore` 적용을 확인했다. 원문 입력·응답을 이 문서에 대량 복사하지 않는다.

| 자료 | 확인하는 내용 |
| --- | --- |
| `KR-corpus.json`, `US-corpus.json` | 고정 입력과 작업 목록, 제외된 입력 |
| `KR/US-spark-original.json` | 기존 입력에 대한 Spark 실응답 |
| `KR/US-spark-compact.json` | 1차 축약 입력에 대한 실응답 |
| `KR/US-spark-v2-low.json` | 재설계 입력 + reasoning effort `low` 실응답 |
| `KR-full-metadata.json` | 전체 KR 빌드의 모델 전달, 호출, 종료 상태 |
| `KR-full-engine.json` | 전체 KR 빌드의 보고서 데이터·결측 상태 |
| `probe.py`, `full_acceptance.py` | 재현에 사용한 호출·관찰 스크립트 |

표의 `KR/US-…`는 시장별 두 파일을 뜻한다. 저장 입력 probe는 핵심 산문,
자금 흐름, 저장된 중기 후보만 대상으로 한다. 기사 전문, 전체 Telegram 피드,
후보 심층 해석, 채널 종합, 휴장 종합, 이미지 해석, 전체 HTML 빌드는 이 probe의
평가 범위 밖이다. US의 `digest_prose`는 입력이 없어 실행하지 않았다.

`automatic_pass`는 파싱·완전성·기존 검사 결과다. 경고가 남아도 통과할 수 있으므로
사실성 점수나 의미 정확도로 해석하지 않는다. 독립 의미 검토는 원시 `response`를
입력 근거와 대조했다. 특히 v2 중기 두 건은 `raw_parsed`·`checked`에 핵심 첫
문장만 남아 있으므로, 그 필드만 읽으면 원시 응답의 주의 문장과 길이 문제를 놓친다.

## 저장 입력 probe 결과

| 실험 | KR 자동 통과 | US 자동 통과 | 해석 |
| --- | --- | --- | --- |
| 기존 입력 | 13/13 | 5/5 | 독립 검토에서 의미 오류 발견. 통과율만으로 채택 불가 |
| 1차 축약 | 12/13 | 5/5 | KR `midterm_024060`의 기관 순매도→순매수 방향 모순 |
| v2 입력 + `low` | 2/3 | 1/3 | 세 실패는 수집 timestamp 검사 오탐. 별도 의미 검토 필요 |

v2의 여섯 작업은 KR `section_advice`, `money_flow`, `midterm_024060`과
US `exec_summary`, `section_advice`, `midterm_ORCL`이다. 동일한 작업 ID의 기존
입력 결과와 비교한 CLI usage 합계는 다음과 같다.

| 관측 항목 | 기존 입력의 선택 6건 | v2 + low 6건 | 변화 |
| --- | ---: | ---: | ---: |
| 입력 토큰 | 33,975 | 36,542 | 증가 |
| 출력 토큰 | 18,931 | 9,188 | −51.5% |
| 추론 출력 토큰 | 17,388 | 6,619 | −61.9% |
| 호출 시간 합계 | 35.417초 | 31.305초 | 단일 실행 관측 |

**입력 재설계와 추론 설정을 함께 바꾼 실험이다.** 동일 입력에서 `low`만 바꾼
A/B가 아니므로 효과를 한 요인에 귀속하지 않는다. 입력 토큰은 오히려 늘었고
캐시된 입력 토큰도 23,040→4,608로 달랐다. 출력 토큰에는 추론 출력이 포함되므로
두 행을 더하지 않는다. 이 합계를 구독 한도 절감률이나 비용 절감률로 환산하지 않는다.
원본 probe는 CPU 50%, v2는 CPU 25% 제한이었고 다른 검증과 실행이 일부 겹쳤다.
호출 시간 행 역시 동일 자원 조건에서의 성능 비교로 사용하지 않는다.

v2 자동 실패 세 건은 KR `money_flow`, US `exec_summary`, US `midterm_ORCL`이다.
원시 입력과 응답에 같은 수집 timestamp가 있는데, 숫자 검사기가 시간·초·시간대
부분을 숫자표 밖의 수치로 판정했다. 예를 들어 KR은
`2026-09-14T02:39:33.289618+09:00`, US는
`2026-09-14T02:50:08.689894+09:00`이다. **3/6 실패를 모델 환각 3건으로 세지 않는다.**
검사기가 수집 시각과 관측값을 구분하도록 만드는 일과 응답 의미 개선은 별개다.

독립 검토에서 v2의 주요 숫자 오류는 줄었지만 다음 문제는 남았다.

- KR 자금 흐름은 엔진 분류 생성일을 “관측일”로 표현했다. 확정된 숫자 환각으로
  단정하기보다, 분류 기준일과 원자료 관측일의 구분이 모호한 것으로 판단한다.
  4문장·3문단으로 짧은 설명 형식도 지키지 못했다.
- US AAII는 하락 전망 39.3%가 상승 전망 38.0%보다 높은데 “상승 우위가 크지
  않다”고 표현했다. 실제 우세 방향을 명확히 설명하지 않는다.
- ORCL은 입력에서 제거한 숫자를 “수치가 원문에서 제외”됐다고 설명했다.
  입력 가공과 원자료 결측을 혼동할 수 있는 표현이다.
- 중기 원시 응답의 핵심/주의 길이는 KR 61/87자, US 152/144자로 각각 50자
  지시를 넘었다. 다른 섹션과 US 종합 요약의 문장 제한 준수와 별개인 문제다.
- `snapshot.…` 경로와 `stale=true` 같은 내부 표기가 사용자 산문에 그대로 노출됐다.

중기 길이 초과는 표시상 문제에 그치지 않는다. 기존 `tighten_prose`의
`PROSE_MAX_CHARS=140` 문장 경계 축약과 맞물려 두 응답의 `checked`에는
핵심 문장만 KR 65자·US 87자로 남았고 **주의 행이 실제로 누락됐다**.
길이 계약 불준수와 기존 후처리의 상호작용이며, 새 파서만의 버그라고 단정하지
않는다. 반면 아래 전체 KR 빌드에서 기존 입력을 쓴 중기 8건은 모두 핵심·주의를
포함한 80~109자로 정상 표시됐다. 따라서 판단은 “이번 축약 + low 조합도 운영
계약을 충족하지 못했다”이며, Spark 자체가 불가능하다거나 다른 특정 모델이
필수라는 결론은 아니다.

## 전체 KR 보고서 빌드

`KR-full-metadata.json` 기준 전체 실행은 **848.132초, exit 0**이다. 관찰된
Codex 호출은 20건이며 20건 모두 실제 CLI 모델 인자가
`gpt-5.3-codex-spark`였고 비어 있지 않은 응답을 반환했다.
`OpenRouterNarrator.narrate` 호출은 0건이었다. 이 계측은 모든 직접 HTTP·이미지
호출을 포괄하지 않으며, 비어 있지 않은 응답은 의미 정확성의 보증이 아니다.

HTML과 엔진 JSON이 생성됐다. 엔진 JSON의 네 핵심 서술 항목은 모두 `true`,
`narration_status.failed`는 빈 목록, 수집 결측은 `after_hours` 한 건이다.
Telegram 발송은 억제하도록 실행했고, 억제 경계에 도달한 호출도 0건이었다
(`suppressed_telegram_calls=0`, 실제 발송 0건). **전체 US 빌드는 실행하지 않았다.**

20개 Codex 호출 시간의 합계는 99.631초다. 전체 벽시계 시간에는 자료 수집·조회와
보고서 처리가 포함된다. 전체 848.132초를 모델 추론 시간으로 해석하거나 모델이
전체 지연의 주원인이라고 단정하지 않는다. 관찰 메타데이터는 호출 이벤트에서만
갱신되므로, 호출 수가 잠시 그대로인 상태는 정지 여부를 보여주는 heartbeat가 아니다.

이번 실행은 stage의 `data`·`out`·설정을 사용하면서 **운영 저장소의 `quant`를
import**했다. 이 때문에 `__file__` 기준의 누적 뉴스 입력은 운영 `data/news`,
기본 환경 파일은 운영 `.env.local`, 기본 Toss 인증 캐시는 운영 `data/cache`를
참조할 수 있다. 보고서 출력·주요 원장은 stage로 분리됐지만 완전한 파일 격리는
아니다. 코드 사본을 썼던 이전 baseline과 입력·캐시 조건이 같다고 가정하지 않는다.
검증 unit의 `ReadWritePaths`는 stage와 Codex 런타임 캐시만 허용해 운영 입력
경로에 대한 쓰기는 OS가 차단했다.

운영 개장판 서비스의 `TimeoutStartSec=7200`은 발행 전 대기도 포함한다.
이 평가에서 “운영 제한 720초를 초과했다”는 결론을 내리지 않는다.

## 한도와 다음 적용 경계

Spark는 기존 모델의 Fast mode가 아니라 별도 모델이며 자체 사용 한도가 있다.
공식 설명은 [OpenAI Speed 문서](https://learn.chatgpt.com/docs/agent-configuration/speed)의
Codex-Spark 항목을 참조한다(2026-09-14 확인). 실계정 한도는
`codex_bengalfox`의 5시간·주간 버킷을 별도로 조회해 확인한다. 위 토큰 표만으로
계정 잔량·초기화 시각이나 일반 Codex 한도와의 관계를 추정하지 않는다.

후속 실험에서는 계산, 수치표, 출처, 관측일·수집일·분류 생성일을 결정론적으로
표시하고 Spark에는 짧은 정성 설명만 맡긴다. 근거가 부족하거나 의미·길이 검증에
실패하면 AI 문단을 생략하고 기존 표를 유지한다. 숫자 검사 오탐을 피하려고
검증을 느슨하게 하거나 날짜 근거를 없애지 않는다.

모델을 적용할 때도 보고서 전용 경계를 둔다. 전역 `CODEX_MODEL`을 바꾸지 않고
`report_cli build/render`의 출력 범위에서만 보고서 전용 모델을 선택하고 복원하는
방향이다. `make_quality_narrator(model=…)`의 인자는 OpenRouter 폴백용이므로
Spark 모델 전달 수단으로 사용하지 않는다. 이는 **미구현 제안**이며, 현재 평가로
Telegram 브리지·AI 트레이더·거래 설정의 모델이나 동작을 바꾸지 않는다.
