# Runbook: 텔레그램 포럼 토픽 레인 설정

지금은 모든 텔레그램 알림·명령 응답이 봇 하나의 채팅 한 곳에 섞여 있다. 이
절차를 마치면 슈퍼그룹 하나 안에 포럼 토픽(Forum Topics) 5개 — **제어실 🎛 /
매매 📈 / 브리핑 📰 / 채널 인텔 📡 / 운영 🚨** — 를 만들고, 각 알림·명령
응답이 정해진 토픽으로만 가게 된다. **절차를 밟지 않으면 아무것도 바뀌지
않는다** — 모든 레인이 지금 쓰는 단일 채팅으로 계속 폴백한다.

레인 5개의 뜻:

| 레인 id | 이름 | 담는 것 |
| --- | --- | --- |
| `control` | 🎛 제어실 | 브리지 명령 응답(`/status` `/balance` `/halt` `/flatten` `/watch` …) |
| `trades` | 📈 매매 | 엔진 체결·강제청산 알림, 세션·전략 손익, 주간 스코어보드, 오늘의 전적 |
| `briefs` | 📰 브리핑 | 아침/마감 리포트, 자동 편입, 승격 토론, 수동/스윙 추천, 마켓 펄스 |
| `intel` | 📡 채널 인텔 | 30분 채널 다이제스트, 오너가 직접 포워딩하는 채널 게시물 |
| `ops` | 🚨 운영 | 워치독, 운영 감시, 백업, 배포 알림, 헬스, 사이클 실패 경보 |


> **봇이 두 개다 (2026-09-05 실측으로 확인).** 알림은 `TELEGRAM_BOT_TOKEN`의 봇
> (**@MR_TRADY_BOT**)이 보내고, 명령(`/here`, `/lanes`, `/status`, 포워딩 수집)은
> `TELEGRAM_BRIDGE_BOT_TOKEN`의 봇(**@claude_aws_trade_bot**)이 읽는다. 슈퍼그룹에는
> **두 봇을 모두** 추가해야 하며, `/here`를 읽는 쪽은 브리지 봇이므로 브리지 봇을
> **관리자**로 넣어야 토픽의 모든 메시지(포워딩 포함)를 받는다. 알림 봇은 일반 멤버로도
> 게시할 수 있지만 관리자로 두는 편이 안전하다. 2026-09-05 첫 시도에서 알림 봇만
> 추가돼 `/here`가 브리지에 닿지 않았다.

## 0. 사전 조건

- 봇은 이미 있다 — `.env.local`의 `TELEGRAM_BRIDGE_BOT_TOKEN`/
  `TELEGRAM_BRIDGE_CHAT_ID`(양방향 브리지 봇), `TELEGRAM_BOT_TOKEN`/
  `TELEGRAM_CHAT_ID`(엔진 알림 봇) — 둘 다 같은 물리적 슈퍼그룹으로 보낼
  것이므로 **두 봇 모두** 새 슈퍼그룹에 추가한다.
- 텔레그램 앱이 포럼 토픽(Forum Topics)을 지원하는 최신 버전인지 확인한다.

## 1. 슈퍼그룹 생성 + 토픽 활성화

1. 텔레그램에서 새 그룹을 만들고(멤버는 자신만이어도 된다), **슈퍼그룹으로
   전환**한다(그룹 설정 → "그룹을 슈퍼그룹으로 전환" — 이미 슈퍼그룹이면
   생략).
2. 그룹 설정 → **주제(Topics)** 를 켠다("Forum" 옵션). 이 스위치를 켜지 않으면
   `/here`가 "포럼 토픽이 아닙니다"로 거부한다.
3. 두 봇(브리지 봇, 알림 봇)을 그룹에 추가하고 **관리자(Admin)** 권한을 준다
   — 포럼 그룹에서 봇이 모든 메시지를 받으려면 관리자여야 한다(일반 멤버
   권한으로는 프라이버시 모드에 걸려 명령을 못 받을 수 있다).

## 2. 부트스트랩 — `.env.local`을 건드릴 필요가 없다

`TELEGRAM_BRIDGE_CHAT_ID`는 오너와 브리지 봇의 **1:1 개인 채팅**으로 설정돼
있다. 텔레그램에서 개인 채팅의 chat_id는 상대방의 user id와 같으므로, 이
값은 곧 **오너 본인의 텔레그램 user id**이기도 하다. 브리지는 이 사실을
이용해, **오너 본인이 보낸 메시지라면 어느 채팅에서 왔든** 허용한다
(`server/scripts/tg_bridge.py`의 `is_allowed_chat` docstring 참고) — 그래서
새로 만든 슈퍼그룹의 chat_id가 아직 어디에도 등록돼 있지 않아도, **오너가
직접** 그 안에서 `/here`를 치면 최초 바인딩이 그 자리에서 만들어진다.
`.env.local` 편집도, 브리지 재시작도 필요 없다.

(다른 사람이 그 새 슈퍼그룹에서 같은 명령을 쳐도 오너의 user id가 아니므로
통과하지 못한다 — 임의의 제3자가 이 봇을 자기 그룹에 초대해 `/here`만으로
스스로를 신뢰 대상에 끼워 넣을 수 없다. 단, **한 번 바인딩된 뒤에는** 그
슈퍼그룹 자체가 허용 목록에 들어가므로 그 안의 다른 멤버도 명령을 칠 수
있다 — 크론 알림 답장이나 다른 식구의 조회 같은 용례를 위해 오너가 명시적으로
선택한 완화다. 이 그룹에 신뢰하는 사람만 초대한다.)

## 3. 토픽 5개 생성 + 바인딩

슈퍼그룹 안에서 토픽 5개를 만든다(이름은 자유 — 표시 이름과 레인 id는
독립적이다, 아래 `/here`가 실제 바인딩을 정한다). 각 토픽 **안에서** 아래
명령을 하나씩 친다:

```
/here 제어실     (또는 /here control)
/here 매매       (또는 /here trades)
/here 브리핑     (또는 /here briefs)
/here 채널 인텔  (또는 /here intel)
/here 운영       (또는 /here ops)
```

성공하면 각 토픽에 `✅ 이 토픽을 <이모지 이름> 레인으로 등록했습니다 (thread N)`
답장이 온다. 실패 케이스:

- `⚠️ 이 채팅은 포럼 토픽이 아닙니다` — §1-2에서 주제(Topics)를 안 켰거나,
  일반 채팅(토픽 없는 슈퍼그룹의 "General")에서 쳤다.
- `❓ 알 수 없는 레인: ...` — 오타. `/lanes`로 정확한 이름/철자를 확인한다.

## 4. 확인

```
/here
```

바인딩된 토픽 목록이 나온다(각 레인마다 `topic <thread_id>` 또는
`미바인딩`). `/lanes`(또는 `/레인`)를 치면 레인별 용도 설명표가 나온다.

크론 알림이 제대로 가는지 보려면 아무 스크립트나 강제로 한 번 돌려본다(예:
`bash server/scripts/ops_watch.sh`) — `NOTIFY_LANE=ops`가 이미 배선돼 있으므로
🚨 운영 토픽으로 가야 한다.

## 5. 마이그레이션 중 동작 (부분 바인딩)

5개 중 일부만 바인딩해도 안전하다:

- 바인딩된 레인 → 그 토픽으로 `message_thread_id`가 실려 간다(헤더 없음 —
  토픽 자체가 정체성이다).
- 아직 안 바인딩된 레인 → 레거시 단일 채팅(`TELEGRAM_BRIDGE_CHAT_ID`/
  `TELEGRAM_CHAT_ID`)으로 폴백하되, **다른 레인이 하나라도 바인딩된 뒤**라면
  한 줄 헤더(예: `📰 브리핑`)를 붙인다 — 여러 레인이 섞이는 방이 됐으니
  구분이 필요해서다. 아무것도 안 바인딩됐으면(마이그레이션 전) 헤더도 없이
  완전히 예전과 동일하게 동작한다.

## 6. 해제 (언바인드)

지금은 전용 언바인드 명령이 없다 — `data/state/tg_lanes.json`을 직접
편집하거나(`threads`에서 그 레인 키를 지운다) 다른 토픽에서 같은 레인으로
`/here`를 다시 쳐서 **재바인딩**한다(마지막으로 등록한 토픽이 그 레인을
갖는다). 전체를 되돌리려면 `data/state/tg_lanes.json`을 삭제한다 —
그 순간부터 모든 레인이 레거시 단일 채팅으로 폴백한다(§5, 마이그레이션 전과
동일).
